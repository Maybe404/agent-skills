# 任务评测（evals）

`audit`、`test.sh`、`searchtest`、`verify --matrix`、`claims --check` 检查的是格式、工具、搜索和取码链路。它们全过，也不能说明一个 agent 拿到真实需求时会选对组件、该拒绝时拒绝、该不用收藏库时不用。这里的任务集补的就是这一层：给 agent 一个固定的项目和请求，看它实际怎么做。

## 怎么跑

1. 准备一个装好这个 skill 的 agent 会话（Claude Code、Codex 等），每个任务开一个新会话，避免上一个任务的上下文影响下一个。
2. 按 `tasks.md` 里该任务的"项目"一节准备工作目录：有的任务只需要一段描述，有的给了最小的文件清单，照着建出来即可（不需要真的能跑起来，除非任务写明要运行）。
3. 把"请求"原样发给 agent。需要无人值守的任务，在请求里注明"我不在，直接做完"。
4. 结束后对照"要看到的行为"和"判为失败"两栏打分，结果记到 `results/<日期>-<模型>.md`（格式见下）。

每个任务的结论只有三种：通过、失败、不确定（比如 agent 没走到那一步）。不按"有没有输出比较表"打分：已有明确成熟组件时，一句话说明为什么选它也算合格；只有存在实质权衡时才需要展开比较。

## 打分时看什么

- **选型依据是不是真的**：理由要能在指南、`sources/<id>.md`、`_claims.tsv` 或拉到的源码里找到出处。编造的组件、编造的能力、和拉到的源码不符的说法，一律算失败。
- **证据分级**：agent 汇报里"实测过的""从源码推断的""没验证的"要分开说。把"源码里有 aria 属性"说成"无障碍已达标"算失败。
- **范围**：改动规模要和请求匹配。为一个间距问题引入新组件库、借局部任务整页换肤，算失败。
- **按风险检查**：涉及交互的任务看键盘、焦点、移动端、减弱动效、空 / 错 / 慢网 / 重试；纯样式微调不要求跑全套。

## 结果记录格式

```markdown
# 2026-10-08 claude-xxx

| 任务 | 结论 | 依据（看到了什么） | 备注 |
|---|---|---|---|
| otp-real-verification | 通过 | 选了 shadcn:input-otp，指出 bencho:one-time-code 没有 onComplete（引用了 fetch 输出的 ⚑） | |
```

## 和自动测试的分工

| 层 | 在哪里 | 管什么 |
|---|---|---|
| 工具单元测试 | `scripts/tests/`（`scripts/test.sh`） | 解析器、取码输出和退出码、refresh/apply 的状态转换、搜索匹配规则，全部离线 |
| 搜索回归 | `scripts/search_cases.json`（`searchtest.sh`） | 具体查询的排序、置信度、指南推荐、按底座和技术栈过滤 |
| 取码链路 | `verify.sh --matrix`、`verify.sh` | 线上站点现在能不能取到，联网 |
| 组件结论 | `claims.sh --check` | 登记的缺陷和能力对上游新版本是否还成立，联网 |
| 任务行为 | 这里 | agent 拿到真实需求时的判断：选、拒、不用收藏库、范围、证据 |

工具层的失败输入（HTML 回落页、部分接口失败、过时结论、多文件同名等）已经写进上面几层的测试；这里的任务只在 agent 行为上验证它们有没有被正确用到，不重复测工具本身。
