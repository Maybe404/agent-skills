# 经验库（.conductor/lessons.md）

把犯过的错写下来，让后面干活的 worker 一定能读到；同一个错在三个不同的日子都出现过，就升级成硬规则。

## 放在哪里，怎么让 worker 读到

- 经验放在 `.conductor/lessons.md`，不进项目文件，不提交到仓库。
- worker 不会自己去读这个文件：编排者写 brief 时，把和本任务有关的条目摘进"相关经验"一节。
- 升级后的硬规则写进项目自己的规则文件（例如 `AGENTS.md`、`CLAUDE.md`、`code-standards.md`），这样所有 worker 启动时都会读到。改项目规则文件要先征得用户同意；loop 里按建立时的授权执行。

## 条目格式

```markdown
**<一句话规则>**
- <哪个任务 / commit / issue 出的事，后果是什么>
- <修复的 commit>
- Done right: <做对的例子（可选）>
- Seen N× (YYYY-MM-DD, YYYY-MM-DD).
```

示例：

```markdown
**说修好之前，先在报告人使用的界面上原样复现。**
- 任务 #12 返工 3 次，每次只修了截图里的那一个场景。
- 最终修复：a1b2c3d
- Seen 1× (2026-10-05).
```

也记做对的事（Done right），让 worker 读到的除了"别这样"，还有"照这样做"。

## 什么时候记

- 单次任务结束时：出现过返工、审查超过 1 轮、验证被发现不充分、对外承诺后又改口，就记一条。
- 每日复盘时（见 [loops.md](loops.md) 的"清理与夜审"）：把当天的提交和任务全过一遍，只看三类：
  1. 修完又返工的
  2. 本来就不该合的
  3. 验证做得太糙的

## 升级规则

- 同一条教训在 **3 个不同日子**都出现过（Seen 3×，日期各不相同），就升级成项目规则，之后每次审查都逐条核对。
- 再次遇到已有的条目：只更新 `Seen N×` 和日期，不新增重复条目。
- 已经升级的条目从经验库删掉，换成一行指向规则文件的说明，避免两处不一致。

## 不记什么

- 能从 git log 或任务库直接看出来的事实。
- 一次性的环境问题（某天网络断了）。
- 没有任务、commit、issue 作证据的印象。
