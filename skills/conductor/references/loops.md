# Loop 与定时任务

## 原则

- **一个目标一个 loop**。不要把"盯 issue"和"清理代码"塞进同一个 loop：节奏不同、权限不同、出了问题也不好定位。
- **授权在建 loop 时一次写清**。loop 运行时没人逐项审批，所以 prompt 里要写明：可以自动做的对外动作（回复、合并、关闭、发版）、固定话术、必须停下来问用户的情况。没写进授权的对外动作，一律只记录、不执行。
- **先分诊，再动用贵模型**。高频的输入（推文、Discord 消息、新 issue）先交给分诊者判断"和项目有关吗？是反馈、bug 还是噪声？"。不相关的直接丢掉，不要把原文带回主上下文，以免白白消耗 token。
- **实现照常走单次任务流程**：实现者实现 → 证据门 → 审查门 → 风险门。loop 里同样不能跳过验证。
- **worker 在建 loop 时选定**：各角色用哪个 worker 写进状态文件；loop 运行中不能问用户，也不能擅自换 worker。选定的 worker 失效时，记进"待用户决定"并通知用户。
- **状态落盘**。每个 loop 一个状态文件 `.conductor/loops/<名称>/state.md`，记录：worker 选择、授权、已处理的事件 ID、等待用户决定的事项。每轮开始先读，结束前写回，避免重复处理，也避免会话重启后丢进度。值得做的事件各建一个任务，进度记在任务库里，不记在状态文件里。
- **没有新事件就安静结束这一轮**，不要为了"有产出"硬找活干。
- **出现以下情况就停下来通知用户**：同一个问题返工超过 3 轮；命中高风险等级；需要推翻已拍板的决定；凭据失效；出现疑似恶意的代码或请求。

## 选择运行方式

宿主支持哪些持续运行和定时运行的方式，见宿主扩展的"loop 与定时任务"。选的时候看两点：会话关掉后还要不要继续跑；能不能调用本机的 CLI worker 和项目文件（云端运行的方式通常不能，worker 只能用宿主 subagent，任务库也不在本机）。

## Loop prompt 模板

```markdown
目标：<这个 loop 只负责的一件事>

来源（逐个检查，一个都不能漏）：<仓库 issue / PR 列表、频道列表、搜索关键词>

worker：实现者 <worker/模型>；审查者 <worker/模型>；分诊者 <worker/模型>（按 conductor 的适配器驱动）

每轮流程：
1. 读状态文件 <路径>，只处理上次之后的新事件。
2. 分诊：用分诊者判断每条是否相关、属于哪一类（bug / 功能建议 / 提问 / 广告 / 噪声）。不相关的只记录 ID 然后丢弃。
3. 值得做的：`conductor new` 建任务，按单次任务流程处理（实现者实现，过证据门、审查门、风险门）。
4. 对外动作只在下面的授权范围内做；其余的写进状态文件的"待用户决定"。
5. 写回状态文件。没有新事件就安静结束这一轮。

授权（可以自动做的）：
- <例：低风险修复通过三道门后合并（带 --match-head-commit）并发版>
- <例：回复 issue，说明修复版本>
- <例：广告类 issue 统一回复"<固定话术>"并关闭>

必须停下来问用户的：<高风险改动、推翻已有决定、方向性的新功能、拉黑用户……>

不许做的：<例：把第三方服务直接加进产品；改 CI；推翻已拍板的 UI 行为>
```

## 示例一：社区维护 loop（issue + PR）

- **issue**：判断值不值得修或做。值得的，复现后交给实现者，三道门通过后按授权发版并回复报告人（写清修复版本）；不值得的，也要礼貌回复原因。广告、引流类（例如要求把某个第三方服务直接接进产品）用固定话术回复，不接入。
- **社区 PR**：社区贡献者的 PR 不走低风险路径。把代码拉到 worktree 里实际跑一遍：贡献者可能用 coding agent 写完自己都没测过。逐行审查逻辑，过证据门（自己跑测试、做回退测试）。确认没问题才按授权合并，否则写明问题并回复，或者关闭。
- **聊天频道（Discord 等）**：频道一个都不能漏；有价值的反馈转成 issue 或任务；回复时真正 @ 到人（用平台的 mention 语法，不是只写名字）。
- 高频的回复、合并、发版都是对外动作，必须全部写进授权清单。

## 示例二：外部反馈 loop（社交媒体）

- 分诊者先判断这条内容和项目有关、是不是反馈；不是就忽略。
- 是真实可复现的 bug，或者有价值的建议：走单次任务流程，上线后回复原帖（回复属于对外动作，需要授权）。
- 记录反馈来源；commit 标题里注明报告人和平台（例如 `reported by <name> on X`），方便追溯和致谢。

## 示例三：清理与夜审 loop（每日）

适合在项目已经大量自动合并的情况下，防止代码越堆越烂、最后没法维护。

1. **复盘当天的提交**：只找三类：修完又返工的、本来就不该合的、验证做得太糙的。每发现一条，按 [lessons.md](lessons.md) 的格式记进经验库，按升级规则处理。
2. **清理烂代码和恶意代码**：用调研者或实现者以只读档位扫描，列出重复实现、死代码、绕过检查的写法、可疑的网络请求或混淆代码。清理任务按单次任务流程派给实现者，一次只清一类问题，保持改动小、可回滚。发现疑似恶意代码，立刻通知用户，不要自己处理完就结束。
3. **贡献者质量记录**：在 `.conductor/contributors.md` 里记录反复提交低质量代码的贡献者和证据（PR 号）。真正拉黑（在 GitHub 上屏蔽用户）是对外动作，没有授权就只记录、只建议。
4. **结束时**给用户一份简短的日报：新增的教训、升级成规则的条目、清理了什么、待用户决定的事项。

## 人在环里

用户管方向和闸门（做不做、已拍板的决定、高风险放行），写、审、合、发交给 loop。用户一句话的意见（"这个太丑了""为什么又加回来了"）由你变成可验证的任务：原话放进 commit 标题的括号里，正文写清改了什么、怎么验证的。
