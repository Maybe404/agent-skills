# 三道门细则

SKILL.md 里是三道门的规则，这里是执行时的检查清单和细则。

目标：每次改动占用的人力（编排者和用户的时间）更少，同时回滚和事故不增加。修复成本也算人力，不能为了省审查时间把问题推到上线之后。

## 证据门检查清单

由你执行，不能交给作者自证。

- [ ] **命令输出**：测试、构建、lint、类型检查的实际输出，关键命令你自己重跑。
- [ ] **范围**：`git status`、`git diff --stat` 里没有范围外的改动，没有未声明的新依赖。
- [ ] **复现**（修 bug）：在报告人使用的那个界面和入口上原样复现，再验证修好。只修截图里那一个场景，往往会反复返工。
- [ ] **回退测试**（Red check，行为改动必做）：把旧代码放回去（stash 掉实现或 checkout 旧文件），新测试必须失败，失败信息能指出是哪个行为错了。编译不过、测试被跳过都不算。
- [ ] **故意改坏**（Break check，选做）：改坏实现的关键一行，确认测试能抓到。
- [ ] **同类问题**：同一类 bug 在别处是否存在，一并修掉或列出来。
- [ ] **真实使用**：改了外部接入，用真实的账号、配置和接口返回验证。
- [ ] **main 上原本就失败的测试**：按马上要修的 bug 处理，不当作"和本次无关"跳过。
- [ ] **未运行项**：没跑的检查写明"未运行"及原因。

## 审查门细则

**怎么审**
- 按审查者适配器的"审查模式"执行；涉及安全的改动另外跑一遍安全审查。
- 深度按风险：低风险一个审查者；高风险或漏掉一个 bug 代价很高时，多个审查者并行找问题，再由独立的验证者逐条核实，只保留经得起核实的发现。
- 对照 brief 的意图审：解决了问题没有、符合现有设计没有、有没有破坏别的地方。修 bug 要找到根本原因，不接受只压住症状的修法。

**输出格式**
- 每条发现标级别：**Important**（必须处理）、**Nit**（琐碎意见）、**Pre-existing**（不是本次引入的旧问题，不算到作者头上，另开任务）。按严重程度排序；摘要第一句写发现了几个问题，没有问题就直说。
- 每条附证据（文件:行、复现步骤）和期望结果；凭名字猜测、没有证据的标"待确认"。
- 不报纯风格、诊断信息、顺手清理类建议。

**回应与裁决**
- 有未回应的 Important（没修也没写理由），不进入风险门。
- 有争议的发现由你裁决；拿不准就让另一个模型核实，不靠作者和审查者来回辩论。

**收敛**
- 优先级：先抓住真实的 bug，其次才是减少轮数。
- 增量复审用 `git diff <上一轮审过的 sha>..HEAD`，并核对上一轮的意见是否真的解决了。
- 超过 3 轮通常说明方案本身有问题或 brief 漏了约束，回到对齐阶段，不要"再修一下"。
- 多轮审查只用于高风险改动，不要默认每个改动都审很多轮。

**从源头修**
- 征得用户同意后写进项目规则文件、加 lint 规则、改 skill。
- 审查漏掉了问题，事后问：模型当时缺了什么上下文？哪一层本来应该拦住它？把修复落到规则文件、skill 或新检查里，同时在错题本记一条。

## 风险门细则

- 一开始从严，有了证据再逐步放宽。
- CI workflow 文件、用户列出的敏感路径，不管改动多小都至少按中风险处理。
- 低风险的轻量路径只给受信任的作者（用户自己、你派出的 worker）；社区贡献者的 PR 至少按中风险处理。
- 批准后有新提交（worker 又推了一次、手动解决冲突后的合并），之前的批准作废，要重新审、重新批。
- 外部提来的需求和 PR，"该不该做"由用户判断（方向、品味、范围）；不同的方向尽早在讨论里提，不要等 PR 做完再阻断。

## 合并与发版

- 合并：`gh pr merge <n> --squash --match-head-commit <审过的 sha>`。审查期间有新提交，合并就会失败，没审过的代码进不来。
- 打 tag 或发版前：这个 commit 的 CI 必须跑完而且全绿，被后续推送取消的不算。发版太密时 CI 一轮都跑不完，平台相关的失败会连续好几个版本没人发现。
- 当天发版里有不少是在修前一版，说明证据门太松了，记进错题本。

## PR 描述与验收评论

PR 描述至少包含：怎么测试的（Testing）、风险（Risk）、怎么撤销（How to revert）。可以由 worker 填写，你核对内容和事实是否一致。验收结果写成任务库评论；有 PR 时同时留在 PR 评论或 commit 正文里：

```markdown
### Verification @ <sha>
- Tests: `<命令>` → <结果>
- Red check: <旧代码放回去后哪个测试失败、失败信息>
- Break check: <故意改坏了什么，测试是否抓到> | Not run: <原因>
- Real usage: <在什么环境、用什么配置实测的> | Not run: <原因>
- Scope: <改动的文件和范围>
- Risk: <低/中/高>，approved by <用户 / 自动放行依据>
- How to revert: <revert 哪个 commit、关哪个开关>
- Review: <审查者、轮数、Important 发现及处理结果>
```
