# Conductor：开发 → 验证 → 审查 → 交付

用户带着任务调用本 skill：本会话就是这个任务的编排者（owner），进入编排模式，实现类工作（读大量代码、写代码、批量修改、跑测试）一律派给 worker，耦合的活整体交给一个 worker。不带任务调用：只加载规则，按规则判断要不要派发。

本 skill 规定流程。宿主能力见 [references/hosts/](references/hosts/README.md)，worker 怎么驱动见 [references/workers/](references/workers/README.md)，任务和进度用 `scripts/conductor` 记录。编排者自己动手只限于验收需要的读取和命令（看 diff、重跑测试）；worker 交来的东西有问题，打回给它返工，不要替它改。

## 启动

1. **确认宿主**：读 `references/hosts/<宿主>.md`；没有对应扩展，按 [hosts/README.md](references/hosts/README.md) 的通用方式执行。
2. **读设置**：运行 `scripts/conductor config`。有设置就沿用，给一行状态提示后进入流程；没有就做首次设置。
3. **状态提示**只占一行，例如：`conductor · 任务库 .conductor/（已从 Git 忽略）· 实现者 codex · 审查者 宿主 subagent/sonnet · 要改直接说`。

### 首次设置

用宿主的提问能力一次问完：

- **Git**：项目不是 Git 仓库时，问要不要 `git init`。worktree 并行、按 diff 验收、回滚都依赖 Git。用户不同意也能继续，但范围检查只能靠 worker 报告，并行只能在文件互不重叠时进行，回滚要靠用户。
- **worker**：每个角色用谁。用户不选，默认用宿主 subagent。选项列出宿主 subagent 和已有的外部 worker 适配器，外部 worker 附上当前可用性（读 [local-setup.md](references/workers/local-setup.md)，跑一次 `scripts/preflight.sh`），不可用的写明原因。用户选了没有适配器的工具：请用户提供调用方式，按 [workers/README.md](references/workers/README.md) 的"没有适配器时"补一份再派发。

| 角色 | 做什么 | 什么时候需要 |
|---|---|---|
| 实现者 | 写代码、改文件、跑测试、修 bug | 有实现工作时 |
| 审查者 | 换一个上下文审查改动；和实现者用不同的模型更容易发现盲区 | 有代码改动时 |
| 调研者 | 读代码、查资料，结论回到编排者 | 需要调研时；不单独选就由实现者以只读档位兼任 |
| 分诊者 | 高频判断"这条消息和项目有关吗" | 只在 loop 里，选最便宜的 |

问完运行 `scripts/conductor init`（建 `.conductor/` 并写进 `.git/info/exclude`，不改动任何项目文件），再把选择写进设置：`conductor config set workers.implementer <worker/模型>`，其他角色同理。

选定的外部 worker 按适配器的"预检"确认可用：凭据过期是常态，不预检就派，要等任务跑完才发现失败。

无法提问时（非交互、定时任务、云端会话）：沿用已有设置；没有设置就用默认（宿主 subagent，不做 `git init`），并在报告开头写明所做的假设。

## 任务库

计划、进度、审查结论、验收结果、交付记录都写进 `.conductor/` 任务库，不在项目里另建计划或进度文档。

| 命令 | 用途 |
|---|---|
| `conductor list` | 看进度：每个任务一行（编号、状态、风险、更新时间、标题），不用读全文 |
| `conductor show <id> --last N` | 看一个任务的元信息、正文和最近 N 条评论 |
| `conductor new -t <标题> -r <风险> -f <文件>` | 建任务，正文写需求和计划，勾选清单就是进度 |
| `conductor comment <id> -f <文件> --as <署名>` | 追加评论，只追加不修改 |
| `conductor status` / `risk` / `label` / `link` / `body` | 改状态、风险、标签，关联分支或 commit，更新正文（旧版本自动留存） |
| `conductor rundir <id>` | 这个任务放 brief 和 worker 日志的目录 |

完整用法见 `scripts/conductor --help`。派发给 worker 时给出脚本的绝对路径。

规则：
- **一个任务一个条目**。关键节点写一条评论：派发、证据门结果、审查结论、阻塞、需要用户决定、交付。
- **状态流转**：`open` → `in-progress` → `review` → `done`；卡住用 `blocked`，等用户决定用 `needs-user`，放弃用 `closed`。状态、风险、标签、关联、正文只由编排者改，worker 只能评论。
- **原文入档**：worker 的结论由它自己写成评论；只读档位下写不了文件的 worker，由编排者用 `comment --verbatim --posted-by 编排者 -f <它的输出文件>` 原样贴进去，不改一个字。编排者的裁决另写一条，署名是编排者。两者并排，事后才分得清是 worker 判断错了还是编排者裁决错了。
- **署名**：`<角色> · <worker>/<模型>`，编排者是 `编排者 · <宿主>/<模型>`。外部 CLI 在派发命令前设置 `CONDUCTOR_AUTHOR=<署名>`，worker 调用时自动带上；宿主 subagent 按宿主扩展的方式传。
- **经验**记在 `.conductor/lessons.md`，规则见 [references/lessons.md](references/lessons.md)。
- 在项目里新建任何文档（包括规则文件），都要先征得用户同意。

## 单次任务流程

1. **对齐**：和用户说清目标、范围、验收标准、不能碰的东西，定好风险等级。有歧义先问，不带着猜测派发。对齐后 `conductor new` 建任务，正文写需求和计划。
2. **拆分**：能独立验收的才拆开；单条深依赖链、跨文件的一致性（命名、API 形状、措辞）整体交给一个 worker。拆不拆不明显时，用一句话向用户说明选择和理由。
3. **审批**：每个子任务一行：角色、worker 和模型、目录、权限档位、任务、验收标准、风险等级。用户明确同意后才派发；用户要求改的，改完再给一次。
4. **派发**：按 [templates/brief.md](templates/brief.md) 把 brief 写进 `conductor rundir <id>`，按适配器的"派发"执行，任务状态改成 `in-progress`。
5. **证据门** → 6. **审查门**（状态改成 `review`）→ 7. **风险门**：见下一节，每道门的结果写成评论。
8. **沉淀**：出现过返工、审查反复、验证不充分的，记一条经验。
9. **交付**：`conductor link` 关联分支、commit 或 PR，状态改成 `done`。
10. **汇报**：每个角色用了哪个 worker 和模型、各自产出、怎么验收的（命令及结果）、哪些没验证、遗留问题。结论分开写已验证、未验证、推测。

## 三道门

检查清单、审查输出格式、合并发版规则和验收模板见 [references/gates.md](references/gates.md)。

**证据门**：编排者自己验证，worker 说"做完了"不算。
- 测试、构建、lint 的实际输出，关键命令自己重跑；`git status`、`git diff` 里没有范围外的改动。
- 修 bug：先在报告人使用的界面上原样复现；新测试要过回退测试（把旧代码放回去，新测试必须失败并指出是哪个行为错了）；同类 bug 一起修。
- 改外部接入：用真实配置和真实返回验证，没实测过的不能说能用，也不能在它上面继续开发。
- 没跑的检查写明"未运行"，不能省略。

**审查门**：
- 审查者和作者不在同一个上下文；深度按风险定，高风险用多个审查者并行找问题再逐条核实。
- 发现分 Important / Nit / Pre-existing 三级，每条附证据；过滤风格类意见，Nit 只列几条：agent 作者会去修每一条噪声，平白多出几轮。每条 Important 都要修掉或写出不修的理由。一个 bug 当成一类问题来修。
- 第一轮全量审查，之后只审新改动，已经提过的不再重复提：后续轮次反复揪出的问题大多在第一轮就已经存在，全量重审只会兜圈子。
- 审查加修改超过 3 轮仍不过：停止打补丁，退一步重想方案（重写 brief、换做法、换 worker 或模型），或交给用户决定。
- 反复出现的同类意见、审查漏掉的问题，从源头修：征得用户同意后写进项目规则、加 lint 规则或检查。

**风险门**：

| 等级 | 范围 | 放行条件 |
|---|---|---|
| 低 | 文档、文案、只给内部用的功能、藏在开关后面的新增改动 | 证据门和审查门都通过，且用户事先授权过自动合并 |
| 中 | 普通产品改动；缓存、自动更新、系统提示词这类敏感处 | 用户批准 |
| 高 | 登录鉴权、计费、CI 和发布流程、安装程序、密钥、删除数据、对外发布 | 用户明确批准，且另一个 worker 或模型交叉审查过；AI 审查通过不能代替用户批准 |

等级看改动内容，不看作者，拿不准就往高处归。批准只对审过的那个 commit 有效。用户拍过板的产品决定，PR 不能推翻。

## 对外动作

评论、回复 issue 或 PR、发帖、合并、关 PR、打 tag、发版、拉黑用户，都会被别人看到或者不可逆。只在用户明确授权的范围内做：单次任务里逐项确认；loop 的授权在建立时一次写清（能做什么、固定话术、什么情况要停下来问）。

## Loop 和定时任务

目标是持续性的（盯 issue 和 PR、盯用户反馈、每晚复盘、定期清理）就建 loop，一个目标一个 loop。建立时选好各角色的 worker、写清授权，记进 `.conductor/loops/<名称>/`。每一轮：拉取新事件 → 分诊 → 值得做的建任务、按单次流程走（审批换成建立时给的授权）→ 授权内的对外动作 → 更新 loop 状态 → 没有新事件就安静结束。模板和示例见 [references/loops.md](references/loops.md)，宿主支持哪些运行方式见宿主扩展。

## 权限档位

每次派发指定三档之一，按适配器的"权限映射"转成参数。不要依赖 worker 的全局默认：适配器标明全局默认是全权限的，必须显式传参。

- **只读**：调研、审查、出方案。
- **工作区可写**：常规实现。没有沙箱的 worker，brief 里必须写明可改的路径，验收时检查范围外改动。
- **全权限**：联网装依赖、改工作区以外的文件。用户明确同意才用；跳过所有确认和沙箱的参数，用户点名才用。

worker 会改文件时，派发前先 `git status`；有未提交的改动，由用户决定先提交还是改用 worktree。

## 派发、并行与返工

- 外部 CLI 按宿主扩展的"后台运行"方式跑，日志写进 `rundir`，等完成通知，不轮询。等待期间做不依赖结果的事。
- 失败时先看日志，常见原因是凭据过期、模型名写错、额度或订阅失效。如实报告用户，不要自己改凭据，也不要悄悄换成用户没选的 worker。
- 会改文件的 worker 不在同一个工作树里并行，除非文件范围互不重叠且 brief 里写明了各自能改和不能改的文件；否则每个 worker 一个 git worktree，验收后由用户决定合不合。只读的 worker 可以随意并行。
- 返工优先按适配器的"续接"回到原会话。指令要具体：哪条验收标准没过、证据、期望结果。
- 同一个 worker 和模型返工一次仍不过，换更强的模型新开会话，附上汇总（原目标、已完成的改动、失败原因、当前问题、验收标准）；换成用户没选的 worker 先问用户。超过 3 轮按审查门退一步重想；还不行就把任务标成 `blocked`，告诉用户卡在哪，不要自己硬改，也不要降低标准。
