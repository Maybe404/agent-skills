# Brief 模板

worker 没看过编排者和用户的对话，brief 是它唯一的上下文。复制下面的骨架，写进 `conductor rundir <id>` 给出的目录，再按适配器的"派发"执行。

用户可见的文案，描述要满足的行为，不给样例字符串（worker 会原样照抄）。

---

```markdown
# 任务 #<id>：<一句话>

## 目标
<要达成的可观察结果：用户或测试能看到什么。>
<已经知道修法时：建议用 X；验收标准是 Y。指定了做法，也不收窄验收范围。>

## 背景
- 相关文件：<路径>
- 已确认的决定：<和用户定下的，不许推翻>
- 试过又放弃的方案：<方案及原因>
- 相关经验：<从 .conductor/lessons.md 摘出与本任务有关的条目>

## 范围
- 可以改：<文件 / 目录>
- 不许改：<文件 / 目录>，以及 `.conductor/` 下除评论以外的任何东西
- 不许做：提交、推送、安装依赖、删除文件、改 CI（按需保留）

## 验证（你自己跑，把输出写进结论）
- <测试命令>
- <构建 / lint / 类型检查命令>
- 修 bug：先写一个能复现问题的测试，确认它在旧代码上失败，再修。
- 跑不通就如实报告。跳过测试、放宽断言、硬编码结果、注释掉代码都算绕过，不允许。

## 提交结论
结束时把结论写进一个文件，然后提交到任务库：
`<conductor 绝对路径> comment <id> -f <结论文件>`
（署名由编排者设置：外部 CLI 通过环境变量自动带上，不要自己加 --as；编排者在这条命令里写了 --as 的，照抄。命令失败就把结论作为最终回复输出。）

结论包含：
1. 改动的文件列表
2. 每条验证命令及其结果（贴关键输出）
3. 没有运行的检查，写明"未运行"及原因
4. 你的判断：做到了什么、没做到什么、你认为有风险的地方
5. 未解决的问题和建议（只写，不动手）
```

只读档位的 worker 写不了文件，删掉"提交结论"里的命令，改成"把结论作为最终回复输出"，由编排者原样入档。
