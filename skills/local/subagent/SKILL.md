# 派发 subagent

本次要编排的任务：$ARGUMENTS

上面一行有内容时，本会话进入编排模式：你只做需求澄清、方案拆解、任务分发、结果验收；实现类工作（读大量代码、写代码、跑测试、批量修改）一律派给 subagent，"大约 5 次以内自己做"不再适用；耦合的活整体交给一个 agent。上面一行为空时，只按下面的规则派发，拆不拆按"拆什么"判断。两种情况下，派发前都要经"怎么派"的审批。

## 拆什么

拆给 subagent：多个独立文件或目标；重复和机械转换；独立验证；对同一问题的多路独立尝试（采用哪个由你定）。留在主循环：对话、规划、权衡、验收；大约 5 次工具调用以内能完成的活；单条深依赖链和跨文件一致性（命名、措辞、配色、API 形状）必须由一个上下文完整处理——要么你自己做，要么整体交给一个 agent。两边都符合：留在主循环。
拆出来的每个任务都要对应一个可独立验收的结果；探索性任务的验收物是报告本身。subagent 运行期间，你继续做不依赖其结果的工作，不空等。工作清单事先已知的流水线（分发→验证→汇总；迁移；审计）用 Workflow，先向用户提议，批准后再启动。启动 Workflow 前，先用几次工具调用把工作清单列出来，确认每一项都已知——workflow 中途不会停下让你改主意。
拆不拆不明显时（看着能拆但留下，或反过来），开工前向用户用一句话说明选择和理由。

## 派给谁

按所需推理深度选模型，不按重要性。Sonnet：需要推理或判断的常规任务，默认档。Opus：深度推理、影响面大、正确性难判断、架构。只因思考更深才升 Opus，不因任务重要。subagent 的名称附模型简称：`xx任务 A-Sonnet5`。

## 怎么派

启动任何 subagent 或 workflow 之前——包括用户明确要求拆的——先向用户展示每个 agent 的方向、任务、模型等易懂的简要概述，等用户明确批准再派；用户要求修改的，改完重新展示。启动后才发现 prompt 错了，损失已经发生。resume（用 SendMessage 续用已有 agent，保留它的上下文）不算启动。
给 subagent 的验收标准写成可观察的结果——用户或测试能看到什么——不写实现方式：给它"做 X"，它只验 X；给它"达成 Y"，它会自己找机制，包括没人指给它的文件。你已经知道怎么修时，把修法作为建议写进去，验收标准另写（"建议用 X，但标准是 Y"）——指定了做法也不能收窄验收范围。对用户可见的输出，描述要匹配的行为，不给样例字符串——subagent 会把样例原样复制。要求 subagent 验证结论时找反例，不找支持证据。codegraph 可用时，在 prompt 里注明 codegraph 可用。要求 subagent 在报告末尾附：改动文件、未解决问题、后续建议（只写，不动手）。
多个 agent 在同一工作树并行时：在 prompt 里给每个 agent 指定可改和不可改的文件；它需要改别人的文件时写进报告，不直接改；提醒它整体 typecheck（类型检查）或测试会报出别人正在改的文件。

## 打回

subagent 的结果有问题需要返工时：优先 resume 持有相关上下文的 agent（通常是产出它的那个）。它的上下文超过该模型窗口的 40% 时不再续用，改为新开 agent，附上你写的汇总：原目标、已完成改动、试过又放弃的方案及原因、当前问题、验收标准；路径、名称、数字等精确细节原样保留。上下文用量自己算：用 jq 从它的 transcript 里只抽 usage 字段，最后一条 assistant 记录的 input 加 cache 就是当前值；不读 transcript 正文，也不问它。同档打回一次仍未解决，换更高一档模型新开（附汇总）；已经是 Opus 的，你自己做。
