# 选型指南模板

每个 UI 任务一份 `guides/<task>.md`，`<task>` 用 `scripts/ua.py` 里 `TASKS` 的取值。中文写作，组件 id 和代码保持英文。正文不写一级标题以外的套话，每条结论都要有依据（看过的源码、文档或实测）。

证据怎么写：
- 每条组件结论标明依据：已拉源码（写日期）、catalog 或文档、未验证。读过源码不等于做过键盘、读屏、触屏实测，没做的照实写"未实测"。
- 要求接入方改上游代码的、决定能不能直接上线的、几份指南都会提到的结论，登记到 `sources/_claims.tsv`（格式见 `sources/_SPEC.md`「结论台账」），指南里写一句话结论并引用它；同一事实不在多份指南里各写一份配方。
- 不写行号定位（"第 179 行"），用文件名、选择器或函数名，上游一改行号就失效。
- 写完跑 `scripts/claims.sh --pending`，看有没有和其他指南说法不一致的组件。

```markdown
# <中文名>（<task>）

## 什么时候需要
一两句：这类组件解决什么问题；什么情况下其实不需要（比如能用文字或原生控件解决）。

## 默认推荐
| 主底座 | 推荐 | 理由 |
|---|---|---|
| shadcn | `source:id` | 成熟度、可访问性、依赖、和底座的一致性 |
| uiarc | `source:id` | … |
| 没有底座或其他 | `source:id` | … |

## 按场景换
| 场景 | 推荐 | 理由 |
|---|---|---|
| 某种页面模式或需求 | `source:id` | 为什么这里换它更好；需登录的条目不放推荐列，写成"登录后可换：`source:id`" |

## 慎用
- `source:id`：原因（第 1 级硬伤、第 3 级审美风险、依赖太重、和主底座冲突、实现不成熟……），以及什么条件下仍然可以用。

## 页面模式约束
- Persuade / Operate / Read / Experience 下分别能用到什么程度（引用 `_scenes.md` 的效果预算）。

## 接入要点
- token 映射、可访问性（键盘、焦点、ARIA、对比度）、减弱动效、移动端、性能，以及这一类最常见的坑。

## 候选清单
按"默认推荐 → 场景替换 → 其他可选 → 仅参考"排序，每条一行：
- `source:id` — 一句话说明适合什么
```

不需要列出这个任务下的全部条目（用 `find.sh --task <task>` 就能看到全部），只列经过判断、值得推荐或需要提醒的。
